### Journey
As a contributor I went to Projects, Fleet and the glossary first. On the front, every Web4 statement is in-bounds: "an open standard … a shared vocabulary, or ontology", Hardbound as "hardware-bound oversight", and "governance" used only for Hestia and Hub. None of the canonical acronyms appear on the front. My sweep of all 16 pages found one expansion per term. LCT, MRH, ATP and ADP are always the canonical packet/horizon/token forms. T3 and V3 are always the Trust Tensor / Value Tensor, with the dimensions given after a dash. R6 is the arrow form and R7 = R6 + Reputation. There are zero hits for Lifelong, Lifecycle-Continuous, Trust-Tracing, Linear Context, R5 or production-ready. Every architecture/infrastructure/stack near "Web4" is a negation or a labelled upstream quotation. Every unification/scope-inflation hit is a rejection of the word.

**Then I took up the question Passes 1 and 2 left open: does Web4 need a chain?** I checked it against the normative spec, not against the site:

- **The spec says no chain is required.** LCT spec §3.4 (since web4 #945, 2026-10-28) derives `lct:web4:mb32:b…` from the binding public key. It says an LCT "MAY be minted offline, air-gapped", and §3.4.5 forbids a coordinating allocator. §4.2 and §8.1 make `genesis_block_hash` "RECOMMENDED, not required … omit if no blockchain anchor is available". `atp-adp-cycle.md`'s terminology note gives the right general form: units "can be implemented as blockchain tokens, local ledger entries, or other locally appropriate means". So the glossary's "Web4 requires no chain" is **correct**.
- **Upstream still has chain residue, in two places:**
  - The *same* LCT spec still has an unconditional step 4 in §4.1, "Anchors to genesis_block_hash", under "the primary way LCTs are created". Its §7.1 lifecycle reads "Society → Blockchain: Mint LCT", and §12 plans "LCT migration between blockchains".
  - `docs/305-patent-applicability.md` (2026-02-22, the patent crosswalk) defines **"Linked Control Token (LCT) — Non-fungible blockchain token paired with at least one other identifiable data record"**.

  The web4-core README's "LCTs are inherently blockchain tokens" has those ancestors, not the normative text. The site has 0 hits for "Linked Control".

**Then I checked the site's own chain sentence against SAGE's code.** `/notebook/projects` Quick start step 2 says a SAGE instance's `lct://` string "is not a bound, witnessed LCT (… web4_lct_id stays null unless chain registration succeeds, and ACT is stalled)". That frames ACT's stall as the only thing between a SAGE instance and a bound LCT. The bridge that would write `web4_lct_id` (`sage_web4_lct_bridge.py`, unchanged since 2026-03-07) shows otherwise:
- `legacy_to_web4_lct_id()` builds the id by string concatenation, `lct:web4:society:sage-<machine>-agent`. That is a **name-allocated** id: not key-derived and not mb32, the exact thing §3.4/§3.4.5 now forbid.
- The LCT document is built with `public_key="sage_sprout_mock_key_placeholder"` and `binding_proof="cose:mock_proof_placeholder"`.
- The birth certificate lists two witnesses (`lct:web4:society:dennis`, `…:claude`), where §4.2 requires ≥3.

So if the chain came back tomorrow, registration would mint a non-conformant id against a mock key. The bridge predates §3.4 by about 7 months. That is drift between upstream code and upstream spec, but the site's sentence passes it on as "just stalled".

By contrast, the hub really does follow §3.4. `hub-lib/src/ids.rs` has a `CanonicalLctId` that must start with `lct:web4:mb32:b` and carry a 52-character sha256/base32 body, and it has deliberately no conversion from the member UUID. `/notebook/fleet`'s "the hub derives the member's canonical LCT id from the pinned key" is **accurate**.
