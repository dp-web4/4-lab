`/fleet` is clear: there's an eight-row table, and "Monocultures are fragile" is a stated design reason I can accept. `/principles` reads cleanly; the six headings are memorable. `/links` is short and does its job, apart from the 404 and "everything public". `/notebook` explains the two layers well ("If you are an AI reader, start here"). As a human, I liked being told the front pages are the summary.

I never found out what SAGE stands for on the front. The glossary has it, "Situation-Aware Governance Engine", and SWE = software engineering. That's fine by the site's own design, since the front links down. As a newcomer I'd have guessed neither.

*Method note: page text came from live HTML (curl, tags stripped, Python regex), not from WebFetch summaries. Upstream claims were checked against the public repos via `gh api` (web4, SAGE, hestia commits, `CANONICAL_TERMS_v1.md`, `atp-adp-cycle.md`, hestia `PRD_ASSURANCE.md`, hub README) and against the crates.io and PyPI JSON APIs.*

### Journey
I went straight to `/notebook/projects`. The equation renders correctly, the glyph legend is attributed (T3/V3 half to whitepaper §3, ATP/ADP half to the site), and every acronym is canonical. I then tried to catch the cards out against canon and the spec.

**Checks that came back clean (dead ends worth recording):**
- *ATP recharge "updates the producer's T3/V3".* Canon's R6 entry says R6 is the ATP→ADP transaction "without reputation tracking", so an unconditional T3/V3 update looked like R7 leaking into R6. It isn't. `atp-adp-cycle.md`'s R6/R7 note says T3/V3 deltas on the direct participants are an ordinary R6 Result, and that R7 adds the cross-scale reputation feed. The `/notebook/context` R7 row already quotes exactly this boundary. Correct, and finer-grained than canon's one-liner.
- *T3/V3 structure.* "Root node in an open-ended RDF sub-graph, not a scalar", "complementary, not combined", "6-dimensional reputation space at the root level". These match canon verbatim. SAGE's peer tracker is honestly called "a scalar approximation of a non-scalar canon object".
- *Quick start.* `python3 -m sage.instances.init --machine … --model … --operator-name …` matches the argparse flags in upstream `sage/instances/init.py`. web4-core is 0.4.0 on crates.io (2026-10-15) and 0.3.0 on PyPI, exactly as the card says.
- *Front `/fleet`.* "Its being improves the SAGE code it runs on" (Legion) is sourced on `/notebook/raising` (15 `legion-being/*` PRs, #63–#412). "Find each other through a shared directory" is sourced on `/notebook/fleet` ("a fleet manifest — a phone book, not a command center").

**Where upstream has moved and the notebook hasn't:**

1. **SAGE beings can now run code (2026-10-18).** SAGE `fcd222fd1` (merged as #470, quoting a dp ruling) put a `run` verb on main. It is on by default for every being and runs a staged copy of one `.py` file plus up to 8 data files under bwrap: no network, no home, a 1-hour limit and a memory cap of half of RAM. It brings the toolset to 35 verbs. Follow-ups #472–#474 add a macOS Seatbelt path and `request_run`. The commit says legion-being has used it daily since 2026-09-16. The notebook has **0 hits** for "sandbox" in this sense, or for the verb. Front `/raising` says a being acts "only through a small set of governed tools: writing its journal, messaging another being, reading and changing code in a workspace of its own. Every one of those actions is checked against rules before it happens." Executing code is not in that list. A `run` is checked once as a verb, and what the code does during its hour is *contained* by the sandbox, not checked action by action. For a Web4 contributor, this is also the first SAGE effector that is OS-isolated (A3-shaped on Hestia's ladder) rather than A1/A2-shaped.
2. **Two referents for "being".** The glossary's Being row puts a being's records under `sage/instances/<machine>-being/`. `/notebook/raising` and SAGE's AGENTS.md use the word the same way: the heartbeat/gateway instance. But `/notebook/fleet` uses "being" only for the raising line, glossing it as "the operator's shorthand for the line's identity record and history". The glossary's counting nouns (machine → instance → line → session record) never place `<machine>-being` in the hierarchy. Front `/fleet` sends readers to the notebook for "the state of each machine's being", and they land on raising-line states. Legion shows the gap: its line is "quiet" since 2026-09-02, while legion-being opened PRs through 2026-10-09 and runs code daily. Upstream, every machine does have a `-being` instance; GitHub commit search hits: thor 527, sprout 243, cbp 199, hub 83, mcnugget 46, nomad 22, pub 8, plus legion. So the front's "each machine runs its own persistent AI being" holds, but at a referent the fleet page doesn't track. Pass 1 today checked that front claim against raising lines, which shows the conflation spreading into the audit itself.
3. **"Enforcement today" leaves out Hestia.** The Hardbound card, the `/notebook/context` Hardbound section and `/notebook/autonomy` all say fleet enforcement today is "scoped credentials, the track registry, and dated audit logs reviewed after the fact".
